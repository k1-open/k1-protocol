# K1 Protocol Errors

状态：基于 K1 GATT v1.11 和设备端源码的公开草案  
说明：当前协议只定义了通用 ACK/NACK 码。完整设备错误码仍待补齐。

## 1. 通用 ACK/NACK

ACK 帧的 FrameType 为 0x03，Payload 长度为 2 bytes。

| 偏移 | 长度 | 字段 |
|---:|---:|---|
| 0 | 1 | ack_code |
| 1 | 1 | ack_frame_type |

### 1.1 ack_code

| 值 | 名称 | 含义 | APP 处理 |
|---:|---|---|---|
| 0x00 | OK | 数据已接受 | 结束当前请求 |
| 0x01 | CRC | XOR 校验失败 | 重新组帧并重试 |
| 0x02 | BUSY | 设备忙 | 延迟后重试 |
| 0x03 | INVALID | 帧类型、长度或参数无效 | 修正请求，不应原样重试 |
| 0x04 | FULL | 接收缓冲区已满 | 降低发送速率后重试 |

## 2. 重试规则

- 网络超时、BUSY 和 FULL 可以重试。
- CRC 错误应先重新计算校验再重试。
- INVALID 不得原样重试。
- 建议最多重试 3 次，每次间隔 1 秒。
- 控制、OTA 和恢复出厂等有副作用的命令必须做幂等或去重处理。

## 3. 当前错误码的不足

当前 ack_code 只覆盖链路层接收结果，不能区分：

- 电量不足
- 温度过高
- 显示忙
- 音频流未订阅
- OTA 状态错误
- 固件签名失败
- 设备存储空间不足
- 权限不足

这些错误需要后续扩展为稳定的扩展错误码，不应只通过日志文本判断。

## 4. 错误处理原则

1. 错误码必须稳定，不能随意改变含义。
2. 新增错误码只能追加，不复用旧编号。
3. 响应必须指明对应的 FrameType。
4. 设备不得静默丢弃格式正确的请求。
5. 日志可以包含诊断上下文，但不得包含密钥、Token、客户数据或设备私钥。
